# 两阶段效果与验收口径

本文件是工程目标和条件估算，**不是上线结果或时延承诺**。

## 第一板块能验收什么

- summary 正确接线，身份/profile/usage 语义一致；目标响应线上实际使用 gzip，完整解码、实际字节减少。
- 可可靠映射的图片不再占据 cards/相应 details JSON；失败保留 inline，报告真实转换率。
- URL 图片进入视口才 fetch；闭合 Thinking 延迟首次 Markdown 工作；覆盖消费者后停止无需求 details。
- 纯图片补丁通过时，一次受理始终同一 durable row/UID；不承诺断线未知提交自动重发 exactly-once。
- Noting 正常原生预算结束走原 Commit Gate。合法空工作态可以是空 Snapshot，不承诺笔记质量。

## 合理预估

原 cards 864734 B → 离线 gzip 545572 B，少约 36.9%。按现场 13–16 KB/s，545 KB 仍需约 34–42 秒正文传输，再加 headers。**只做 gzip 不够秒开。**

最大潜力是验证型图片 refs：约 651 KB data URL 不再阻塞同一 JSON，summary 与按需 details 减少竞争。今晚保留 200 行，不能预先保证关键响应小于 100 KB。先测新关键编码字节 B，再按 B/现场速率 + headers + 解析渲染估计。

如果实际关键历史落在 50–100 KB、速率仍为 13–16 KB/s，则正文约 3–8 秒；加 2–8 秒 headers，约 5–16 秒量级。这只是条件示例。首次 JS/CSS、登录恢复、额外串行请求和图片自身耗时另计。

合理期待：可转换大图时，先看到文字和操作明显提前，图片随后完成。若关键大图无法映射、慢在登录/握手或连续卡顿，不能保证大幅改善。

## 第二板块初始目标，待实验后校准

| 场景 | 目标 | 条件 |
|---|---|---|
| 已访问会话重开 | 本地历史 300–500 ms 可读 | 需设计持久缓存、身份隔离/版本，不能把旧内容当最新运行态 |
| 本地点击反馈 | 100–200 ms | 不能伪造服务端受理，产品表现保持 |
| 小量变化 | 压缩后优先 8–16 KiB 级 | 真实控制事实齐全，媒体/完整详情分离 |
| 无历史缓存恢复 | 小包链路正常时争取几秒可用 | 不等于首次下载整套 SPA，启动包也须预算 |
| 断网/后台恢复 | 已知内容可读，只补缺口 | 不重复提交；删除/rewind/compact/Gateway 写入都正确 |

13–16 KB/s 下，8–16 KiB 正文约 0.5–1.3 秒；若 headers 本身等 8 秒，无法承诺新数据 1 秒到达。缓存改善已知内容可读，增量减少必须传输的量，好入口改善路径。冷启动 HTML/JS/CSS 不可混入单次增量预算，不能凭空承诺 32 KB 包含当前 SPA。

## 最少记录指标

同机、同会话、相同数据窗口：点击到文字可读；服务端受理到用户行可见；bootstrap/WS open/runtime ready/历史完成阶段；关键压缩 bytes、背景 details、图片 bytes 分开；完成/失败/主动取消/诊断 30 秒中止分开。

少量样本逐一列出，不宣称稳定 p95。第一板块只做与改动相称的验证；第二板块验收随结果和设计最终确定。
