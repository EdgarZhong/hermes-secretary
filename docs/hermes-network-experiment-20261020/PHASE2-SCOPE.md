# 第二板块：实验后设计的完整重构范围

本文件明确重构要解决的问题和决策依据，**不在本轮锁定最终架构或开始实现**。输入为第一板块部署后的真实手机结果，以及已尝试网络改善的有效性。用户允许大幅修改内部架构和原生 API 契约，前提是产品表现/交互保持。

## 1. 与第一板块成对的边界

| 目标 | 第一板块复用现有机制 | 第二板块可重构 |
|---|---|---|
| 历史轻量 | summary、gzip、可靠已有 refs | 面向显示的轻量 bootstrap、版本/cursor、分页边界重做 |
| 图片 | 已验证引用+既有下载，失败 inline | 完整媒体资产化、稳定 ID、尺寸/缩略图/原图、存储生命周期 |
| 详情 | 复用显式打开补水 | 与窗口/优先级/带宽预算协调的详情契约 |
| 渲染 | 延迟首次 Markdown、稳定对象引用 | 全列表窗口化、滚动锚点、增量 Markdown/大工具结果渲染 |
| 受理 | 同次提交原 durable row 认领修复 | 明确命令 ID/幂等边界/receipt 与结果未知恢复 |
| 恢复 | 保留现有权威顺序 | 控制态和历史分离、持久本地可读、差量恢复与 gap |
| 认证 | 必要分段诊断/明确小缺陷 | 结构化 bootstrap、认证/网络/运行态明确区分 |
| Noting | 已知预算结果分类修复 | 仅在需求证明确有必要时处理跨宿主可靠状态传播 |

前端可直接按新显示契约获取轻量状态，后端负责生成事实和增量；不能只给前端做占位，后端仍传同一大块 JSON。

## 2. 必须处理的核心事实

- Web、微信 Gateway 等写入都要可发现；不能把 Web 进程内事件当整个 SQLite 的唯一事实。
- 编辑/删除/Rewind/compaction/祖先会话和 Session rotation 不能用“最大 row ID 以后追加”糊过去。
- 持久事件或可重建差量要有明确版本/保留窗口/gap 语义，不能用 SSE reconnect 自带可靠性。
- 命令结果未知时不能自动再执行模型；本地 pending、服务端 durable receipt、运行态事实要一致。
- 已有内容可以先展示，但不知道 Agent 是否运行时，不能把 unknown 直接当 idle。
- 本地缓存按身份/Profile/session 隔离，登出/账号切换和数据撤销语义明确。
- 产品的消息内容、操作、附件、滚动、折叠、Stop/Steer/Rewind 和 Secretary 行为维持。
- 旧的第一板块改动应能自然保留或被新契约吸收，不制造两套永久权威。

## 3. SSE 与 WebSocket：按结果决定

SSE 是 HTTP 服务端单向事件流，客户端命令仍需 HTTP 等上行机制。EventSource 可重连并传 Last-Event-ID，但可靠补齐需要服务端事件/状态保留；它不替代幂等和一致性设计。

| 实测表现 | 候选决策 |
|---|---|
| WS 小事件与恢复稳定，主要慢在大 REST 历史 | 优先保留聊天 WS，把轻量数据/增量/媒体拆分做好 |
| WS 升级/断线恢复明显差，同路径 HTTP 流反复稳定 | 评估 SSE 下行 + 小 HTTP 命令；同样 payload/恢复语义公平比较 |
| 路径对小请求/两种流都差 | 先承认线路约束，缓存/最小状态/恢复优先；换名称不提供带宽 |
| 必须承载终端/PT Y 等双向字节流 | 该实际功能保留 WS；不能因为 dashboard 用 xterm 就强制聊天也用 WS |

最终保持一条聊天事件主通道或一个明确传输适配层，避免永久 WS/SSE 双发造成重复事实。已有终端功能存在才保留其 WS，不凭空为当前 UI 添加终端。

HTTP/2 中多个流共享 TCP 时，丢失数据造成 TCP 顺序交付阻塞；SSE 在 h2 上也不会自动规避。单一 WS 内混入大历史同样会形成应用级排队。需要实际协议/连接证据，不能只比较扩展名或握手是否成功。

## 4. 网络改善如何影响设计

- 小响应稳定：优先极小控制面、差量同步、已有历史即读，不必为弱网重造所有网络层。
- 建连/认证等待很长：首次可读与服务端最新状态解耦，减少依赖新连接/完整 HTML 的 bootstrap；不假装在线。
- 持续下载差：图片/详情彻底脱离关键路径，明确字节/并发预算与取消语义。
- 新公网入口有效：源站仍在首尔，按实际可达性配置一个明确入口；需要真实聊天/鉴权/恢复验证，不拿静态 HIT 作为替代。

## 5. 设计交付应包含

拿到结果后一次性交付：现状到目标映射、显示 API 和事件/命令契约、时序/状态图、缓存/回放/媒体模型、SSE/WS 决策及证据、迁移/兼容/回退、关键字节预算与真实手机验收。复杂度由完整方案承担，不能分散成互相矛盾的临时补丁。

UX_ACCEPTANCE.md 的 300–500 ms 本地可读、100–200 ms 本地反馈和 8–16 KiB 增量是初始目标；先校准实际瓶颈，不能承诺物理上不可达到的实时到达。
