02 / 概念地图企业 → 个人

从“资料分类”走向“共同理解世界”。

Ontology 的帮助在于明确对象、属性、关系与行为。Palantir 进一步把这套语义接到行动和权限上。我们借鉴这套建模方法，保持已有系统的职责边界。

用户持续交流 · Secretary 理解与统筹
追溯正式登记整理与召回提议与核准行动与反馈

Notebook：本 Conversation 的派生工作记忆

Noting 写入；Main 读取。保存当前理解、重要变化及其来源。对提醒和外部任务可保存引用与有时间边界的观察，不争夺正式状态的所有权。

O1概念拆解

分类 → 关系 → 行动

分类：它是什么？

这是一个行动、一段经历、一个未决问题，还是一项决定？严格类型减少维护歧义。

关系：它与什么有关？

这项行动服务哪个目标，等谁回复；这个决定依据什么，后来被什么修正？

行动：谁有权改变它？

改提醒由正式 Scheduler 工具完成。把“预计会完成”写进 Notebook，不产生真实完成结果。

Stanford Ontology 101 区分类、属性和实例；Palantir Action types 将业务操作与状态变更相连。

O2个人场景的修正

人的生活，常常没有完整状态表。

  • 主观性：“我最近觉得和朋友疏远了”是用户的体验，不能改写成对方客观不在乎。
  • 变化性：一段关系和一个偏好会变。新理解应带上时间与来源，不能抹去旧经历。
  • 不完备：没有回复证据，只能说“尚未看到回复”；不能自动判定“被拒绝”。
  • 低负担：用户自然聊天，系统承担归类与链接。信息不必先挂靠某项任务才值得记住。

Information Scraps 展示个人信息的多样与录入负担；以上具体边界是结合用户愿景的设计推论。

O3采用到什么程度

本轮可借鉴

  • 同一事项跨 compaction 保持稳定身份。
  • 有意义的关系：服务于、等待、依据、取代。
  • 正式状态明确 owner，派生索引明确证据。
  • 用真实提问检验模型是否可用。

当前无需引入

  • 一套完整的个人世界图数据库。
  • 把所有聊天句子转换成实体和关系。
  • 复制 NM 的个人档案与跨会话管理。
  • Palantir 平台、OWL / RDF 或新执行引擎。

Palantir 设计建议支持现实语义与聚焦对象；反模式提醒重复概念、来源孤岛与过度通用对象的成本。借鉴其方法不等于其效果已经在 Secretary 上得到验证。

C4结构建议 · 字段尚未定稿

类型负责归类，其他属性按需描述。

这张卡连接“Notebook 分哪些内容类型”和“每种条目怎样记录”两步讨论。原版把分类与字段混列，容易误以为它们都是同一级标签，或每条都要填满。

  • 内容类型：这条是什么，例如行动、情景、认识、决定；用于归类和确定维护方式。
  • 领域／主题：这条涉及什么，例如家庭、工作；可以与内容类型交叉，具体取值与是否必填待议。
  • 类型专属字段：例如行动的负责人、执行状态；其他类型分别设计，不统一套行动字段。
  • 条目关系：例如行动属于某事项、决定取代旧决定；需要关联时引用已有条目。
  • 候选流程字段：长期化目标、审议与写入结果，放在候选记录中；候选仍携带原始内容类型。
一条行动的示意

简述：确认家庭探访日期。类型＝行动；领域＝家庭；负责者＝用户；状态＝等待家人回复；所属事项＝家庭探访；provenance＝对应对话消息。

已有基本单元是简述＋provenance。这里补充的是结构建议；尚未逐类确定字段、必填项或存储 Schema，也不要求把所有属性都做成标签。

分类方法参考：NISO Z39.19 §5.3.4。本卡的属性划分是项目设计建议。

C5语义映射，非迁移方案

保留已确认的内容准入边界。

  • user_commitment / secretary_task：行动＋责任人＋承诺证据。
  • user_reminder：提醒交 Scheduler；必要情景留在对应内容中。
  • watchpoint：定时观察由 Main 登记；用户的问题与关注缘由分别按语义保存。
  • open_question / formulating_insight / decision：承载用户的问题、认识与决定；模型自己的猜测和未答澄清问题不进入。
  • constraint：用户决定的约束归决定，客观条件归情景。

旧 insight 的用户来源边界已有确认；不能因可带 uncertainty 字段，就扩大为模型未确认的个人解释。

C6下一步设计

互斥还需要退出规则与可见依据。

  • 防积压：建议情景只保留当前仍有理解价值、且未由候选或长期体系承载的内容；失去用途的派生条目应退出，不能只因“曾经发生”无限积累。
  • 候选被否决／撤回：建议有当前用途则移回情景，否则清理；具体规则待讨论，不能同时留在两区。
  • NM 已有内容：需要让 Noting 能识别可见的召回来源与正式写入回执；不能假定它能查询整个 NM，或已经实现语义去重。
  • 新变化：同一个人出现新的经历，不自动等于重复记忆；建议只整理新增／修正部分，避免把整段旧记忆抄回候选。

例如，“家人正在搬家”若已入 NM，Notebook 不再维护其副本；“探访日期仍待确认”是一项不同的工作状态，可以由事项／行动继续承载。

C7用户已明确 · 认识示例批注

问题、认识、决定，属于用户的研讨。

认识由用户自己明确表达，或由用户明确认可双方／模型提出的内容。用户也可以说“我怀疑……”，应保留这种确定性；模型单独猜测不因此取得用户来源。

后续相关讨论中，Main 应能找回用户已有认识、原来的限定与来源，并适时提起。

既有口径见 文案提案 §4／§5.2；提示词实现尚待审。本白板初版将模型猜测放入“理解”的示例已撤回。

C8单独承载，位置待议

只记自己缺什么，不替用户解释动机。

例如：“推迟出发的原因尚未在可见对话中说明；若影响后续安排，先查原文或澄清。”这是一项模型理解缺口，不能写成“用户其实在等家人”。

建议 Main 优先在当前工作中处理；跨压缩仍相关的少量缺口，可放 Compact Message 的独立待澄清区域。补足、被证据排除，或当前工作已不再依赖时关闭。

缺口不进入用户研讨，也不直接变成长期化候选。具体位置、容量及关闭时限待议；Noting 不借此自由生成假说。

C9用户已明确 · 标签继承

从 Notebook 进入长期 Memory，至少继承一个来源类型标签。

认识条目→Memory 候选 · 来源类型：认识→NM Memory · 标签含“认识”

候选携带原始内容类型，Main 在正式提案中展示继承标签，实际写入时一并提交。情景、决定及事务等类型按同样方式对应；主题／人物标签可以补充。

这里的中文标签表示语义对应；具体字符串与受控映射尚未冻结。候选身份不替代内容类型，类型随内容移动也不需要在原区留正文。

04 / 统筹核心从“有个待办”到“理解整个局面”

事项承载结果，行动承载下一步。

Secretary 最重要的能力是持续知道：希望达成什么，谁在做什么，卡在哪里，还有什么可推进。状态要落到合适的粒度。

T1虚构场景 · 状态演示

安排一次家庭探访

结果：确定双方方便的日期与基本行程。约束：先确认家人时间，再订票。

A
确认家人可接待的日期用户已询问；等待家人回复
B
整理两套候选行程Secretary 可并行研究，尚未承诺购买
C
选定并预订依赖 A、B；实际购买仍遵循授权
尚未具备条件

事项仍在推进：A 等待，B 可做。不能把整个事项标成“等待”。

这里切换的是说明性样例，未连接真实任务、提醒或工具。

T2建议保留两个类型

两个类型，能避免几种常见失真。

  • 事项：目标、边界、总体判断、相关行动、关键变化。持续责任也可作为事项，但不强行编造完成日期。
  • 行动：具体步骤、负责者、当前状态、依赖、完成依据。没有上级事项的独立行动也合法。
  • 一个子行动完成，不等于整体目标达成；一个子行动等待，不等于全局停摆。
  • 尚未承诺执行的想法，保留为问题／理解，或在事项中明确“待选择”，不能悄悄进入待办。

GTD 区分结果、下一步、等待与未承诺事项。持续责任等扩展是针对 Secretary 的建议。

T3有限状态，不扩成标签组合

行动建议先用六种状态。

待推进推进中等待条件主动暂缓完成终止

等待条件：记录等谁／什么、条件为何尚未满足。
主动暂缓：明确选择暂不推进，保留恢复条件。
完成：有对应行动完成条件的证据。

未知：不是业务流程的第七状态；信息不足时保留“尚未核实”及最后证据时间。
已委派：是关系与事件；不等于对方接受，也不等于已完成。

Notebook 展示的是有来源的最新已知状态。若外部工具有正式状态，操作前应按需核对；不能用异步索引替代实时工作台。也不新增“所有行动必须用户验收”的普遍门禁。

T4最小结构

只结构化需要稳定查询的东西。

共同基础：身份、类型、简述、provenance、有关对象／条目。

行动补充：负责者、最后已知状态及证据时间；有依赖再带等待对象／条件；有正式任务或排期再带引用。

保留自然语言：复杂理由、人际背景、完成标准、风险与条件先写简述。不要把每条笔记变成一张几十字段的表。

T5需要谨慎建模

“我会做”与“我想做”有区别。

统筹需要识别提出请求、作出承诺、报告完成等不同事件。承诺可以先作为行动的关系与证据保存，暂不新增第八种条目。

如果以后反复出现“一次承诺覆盖多个行动、不同接受条件”的场景，再讨论独立承诺类型。

Winograd 的语言／行动视角支持关注协作承诺。是否拆成独立对象，是我们仍需决定的工程粒度。

总量6,0004,8003,600

数值用于开始讨论，不是已证明的最优值。每次联合 Noting／压缩时检查候选快照的预算，目标 60% 留出增长空间；压缩必要时回原文核对，保留恢复路径。无法安全满足预算时按 L4 处理。

L2退出机制候选

事务看完成，情景看当前用途，研讨看结论是否收敛。

板块压缩／结算时机退出路径
事务完成／终止时，将过程状态收敛成“完成了什么、结果、关键条件、来源”完成记录 → 长期化候选 → 批准并写入确认 → 退出。建议按事项／阶段合并细小行动
情景依据原文合并重复与变化，逐次缩为必要简述＋来源；检查当前用途无当前用途则关闭；值得长期理解则移入候选。关闭表示退出当前工作集，历史事实仍保留
用户研讨问题已回答／撤回；认识由用户后续明确修正或放弃；决定被取代或相关事务结束将用户结论与必要来由收敛后，持久化提案或关闭；模型理解缺口不混入这一板块

事务完成仍需沿已有批准流程写长期记忆。活跃责任与待审候选不因容量紧张被静默删除；Memory 也不以“是否普适可复用”为准入标准。

L3用户已明确 · L3 批注

退出后，只有长期体系承担记忆召回。

  • 持久化：候选经批准、真实写入确认后退出短期体系，后续从 NM／相应目标体系召回。
  • 关闭：未持久化而选择关闭的内容，不再作为可召回记忆保留。
  • 来源取证：长期记忆召回后，可沿 provenance 核对原文；这是长期召回链路的取证步骤。

已撤回旧 Snapshot 搜索及关闭内容的短期恢复方案。候选仍属短期；退出前要明确选择关闭还是持久化。

L4需要明确的溢出行为

有限容量，必须允许显式处理积压。

先去重、缩写，再结算完成项和失效内容；候选相关的提案可以合并。候选仍积压时，让 Main 发起批量审议，不自动批准，也不为腾位置丢掉待审内容。

如果活跃责任和待审内容仍无法安全放入预算，建议返回“容量不足”，保留上一有效 Snapshot 与覆盖边界，由 Main 处理优先级／审议；正常对话继续，新增原文仍保存。

80%／60% 是整理目标。有限容量、不断新增、全部待审项无限保留不能无条件同时成立；接纳与压缩降级策略需要正式确认。

1 · 对齐范围

读取有效快照与新增历史

沿合法 Conversation 路径，明确整理到哪个消息边界。

2 · 识别变化

找新增、修正、解决与取代

优先当前事项和容易被摘要丢掉的限定；按需回读证据。

3 · 整理索引

归类、链接、合并与精简

同一事项保持身份；避免将反复提及的同一事实不断新增。

校验边界与来源后交接

完成有效快照，再由压缩流程携带对应视图进入新区间。

N1建议维护指导

这条信息未来会帮到什么？

  • 恢复统筹：仍需推进的目标、行动、依赖和未知。
  • 恢复依据：选择的理由、适用条件、用户纠正，以及后来变化。
  • 恢复理解：影响当前交流的个人处境、关系和经历；可独立于任务。
  • 支持提案：值得进入 Memory、Skill 或 Rule 的具体材料。

个人情景内容先遵循 C2 的互斥边界：候选或长期体系已经承载的相同内容，不再收录副本。没有实质变化时允许不改，不为填满类别制造内容；重要而难分类的材料不因缺少“任务”而丢弃。

N2共同基元

简述＋provenance，保留必要限定。

简述应让读者知道对象、当前有效表述、重要条件与变化。provenance 可沿用时间范围或 canonical message identities，读取时回到原文及邻近上下文。

示例 · 虚构用户原计划本月探访家人，后因对方搬家暂缓；日期未定。暂停缘由见 E12，后续行动 A7 等待可接待日期。这里不自动推断双方关系恶化。

W3C PROV提供来源与派生关系的通用背景；本轮不改现有 provenance 机制，也不要求采用其序列化。

N3更新规则

维护用户已表达的内容与实际工作状态。

  • 当前摘要随证据更新，保留仍需使用的关键来源。
  • 用户认识须有明确表达或认可来源；用户不确定的语气如实保留。
  • 模型理解缺口独立处理，不写成用户的认识或问题。
  • 新原文和正式工具状态优先，旧 Notebook 不能覆盖。
  • 退出后遵循 L3，不从旧快照恢复记忆。
N4保持退出边界

清退要作出选择：关闭，或持久化。

需要未来召回的内容，先完成长期化流程，再退出短期。选择关闭且未持久化的内容，结束其记忆保留职责。

旧 Snapshot、归档条目和原始历史不另行构成退出后的短期记忆恢复通道。

原始证据的保存不等于继续维护可召回记忆。本轮只修正文档方向，未删除历史，也未修改生产 History 工具。

N5各自保留什么

Compact Message

让模型接着当前工作：近期焦点、当前指令、必要操作状态、紧接着要处理什么。

Notebook

为多个事项、个人情景与重要讨论提供可发现索引：它们是什么、现在怎样、细节和理由去哪里找。

允许少量有用重叠；维护时避免两边各写一份完整会话总结。Notebook 的价值需要以“跨压缩后能否恢复细节”检验。

Anthropic 上下文工程讨论压缩、结构化笔记与按需读取的互补关系；具体分工由 Secretary 的任务决定。

07 / 联合机制两个开关 · 三条触发路径

Noting ＋ Compaction，作为一个联合流程。

用户已明确：普通路径同时触发、并行执行，现有快照获取机制不变。Force 逻辑上同样联合，只有时序差异；Idle 是专门为节约费用增加的自动联合入口。

触发方向已收敛
P1用户已明确

总开关启用联合机制，Idle 只增加自动入口。

  • Noting 总开关关闭：按原生 compaction 逻辑运行。
  • Noting 总开关开启：普通 compaction 同时触发 Noting，并行执行。
  • Idle 子开关：仅在 Noting 开启后可用；决定是否在空闲且上下文足够长时自动联合触发。

关闭 Idle 子开关后，手动压缩与 Force 的联合机制仍有效。职责目标不同，不意味着 Noting 和 compaction 可以独立触发。

P2用户已明确

同时触发，并行执行；快照获取机制不变。

沿用现有父上下文冻结、Anchor 和 Notebook Snapshot 获取机制。Noting 可以多轮调用工具；compaction 保留原生执行链路。

白板初版优先采用“Noting 完成后再启动 compaction”的建议已撤回。

具体完成先后如何衔接既有读取／发布点，在实施接线时核对；本页不另立等待门禁或配对发布协议。

P3沿用现有 Force 机制

达到 Force 线→提前 Force Noting→对应的 compaction

D1第一步 · 范围

Ontology 是整体建模方法。

用它连接人、事项、关系、证据和行动。Notebook 仍负责本 Conversation 的工作记忆；NM、Scheduler 和工具保留各自权威。

D3第三步 · 容量

情景已合并；讨论 6K 总预算是否合适。

D4第四步 · 统筹

两类事务＋少量明确关系。

事项和行动分开；行动带负责人、最新已知状态、必要依赖与证据。正式业务状态来自相应工具或原文，不由 Noting 创造事实。

D6第六步 · 方向已确认

普通路径同时并行；Force 仅有时序差异。
