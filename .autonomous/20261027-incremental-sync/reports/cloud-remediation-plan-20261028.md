### 2.2 修改包 A：恢复与历史一致性闭环

**目标：不仅能“发起恢复”，还必须保证“该提交的提交，不该提交的撤销；有变化会被发现；遇到可恢复边界能结束恢复”。**

原报告确认四个不同接缝缺口：F01 的旧分页绕过取消/认证资格，F02 的 RPC 失效锚点持续复用，F05 的合法 Thinking 尾追加误判，F06 的正式同计数 CAS 改写缺通知。把四者合在一个产品目标下验收，但按前后端文件边界分派。

#### A-FE · 前端读取资格和失效锚点

输入：原报告 §5.1—5.2、§6.4 前端反例；06 C0.2、相关 S/P 条款；既有 REST 锚点不存在与恢复错误语义。

实施内容：

1. **收回所有已失效分页的提交资格。** 将 `loadEarlier` 纳入现有 document/owner/connection/恢复代次及 credentials 边界；网络可取消，返回后提交前仍必须验证资格。不能只加 abort 而依赖传输一定及时结束，也不能只加 UI 隐藏条件掩盖已回写的业务状态。认证清理、断连、owner 变化和取消后，被捕获的旧 HistoryWindows 引用不能继续发布。
2. **只处理确证失效的锚点。** `activate` 正常业务封套 `complete:false / reason=anchor_not_found` 与 REST 404 的既有合法回退语义对齐。撤销失效 selector 及相应复用资格，建立必要最新窗口或新的合法覆盖；后续恢复不能再次由未清的阅读需求/缓存导入同一死锚点。
3. **保持错误区分。** 锚点不存在不等于 Conversation 被删除；暂时网络错误不等于锚点不存在；错误 owner、epoch 或不完整恢复证明仍必须严格拒绝。有效旧锚点和兼容阅读位置照常保留。
4. **维持表现与操作资格。** 正常取消不产生异常 Toast，真实失败仍可观察；恢复成功仍以权威窗口、有限切点和既有布局确认完成，不能提前把 Send/Steer/审批解锁。

关键源码定位（均为原待审 FE 版本）：`controller-page-recovery.ts:467–487, 820–902, 1145–1162`；`page-recovery.ts:181–187`；`controller.ts:897–903, 1024–1027`；App 最终消费 `App.tsx:665–685, 800–804`。

#### A-BE · 后端有限切点与真实写入通知

输入：原报告 §5.5—5.6；06 保留的 D0/S/D1、R3.8 及 C3.1—C3.4。

实施内容：

1. **区分合法尾部增长和旧内容失效。** 在同 owner、同真实 Turn source、旧 Thinking 身份/顺序/内容版本不变的前提下，允许 D1 新增尾部由权威窗口及 native cut 承接。旧 Thinking 原位改写、删除、重排或 Turn 来源变化仍不能沿用旧证明。不能简单删除整个 `latest_thinking` 检查，也不能要求生成停止才恢复。
2. **补齐正式 CAS 改写的提交后通知。** 受支持 writer 实际更新正文/Thinking/详情而插入数为零时，应在成功完成点触发现有历史变更机制。无变化 flush、失败 CAS/回滚不能冒充新成功更新；不另建全库轮询、全历史扫描或持久事件表。
3. **证明“写入 → 被发现 → 页面更新”。** 不能只测主动读取 REST 能得到 delta。用正式可写 replay/CAS 路径，不附带额外 append、新 Turn 或主动页面刷新，让 watcher/现有事件驱动同一页面取得新版本。
4. **保兼容。** 未 opt-in 的 Desktop 调用保持原默认行为，cursor/receipt/身份/版本证明仍有效，临界区不扩展到模型或网络等待。

关键源码定位（原待审 BE 版本）：`tui_gateway/recovery_view.py:193–263, 515–576`；`hermes_state_messages.py:382–392, 463–503`；`agent/transcript_repair.py:149–179, 211–233`；`tui_gateway/change_watcher.py:125–205`。

F06 原审属于静态确认而非已跑完整运行反例。实施者应先补同触发条件的正式失败测试；若发现现有调用方确实补足通知，提交同一前提下的完整反证给独立评审，不为满足“必须有 diff”而修改本来正确的代码。

### 2.3 修改包 B：完整详情与最近 500 条缓存

**目标：已经可靠拿到的内容不会被较薄投影抹掉；容量不足优先保留最新有效内容，而不是只满足“没有超过 500”。**

输入：原报告 §5.3—5.4、前端两个原始反例；06 C0.3—C0.7、D01—D05、S12—S13、P06、C3.3。

实施内容：

1. **统一同身份/同版本的合并规则。** Thinking-only 是字段子集更新，不是完整详情替换。已取得的工具参数、结果和终态字段，在 UID、物理代表行、role 及详情版本匹配时保留，不能因新投影缺字段重新标成 deferred；版本或代表变化时再失效。没有取得过的字段不因合并变成“已完整”。
2. **统一窗口、详情、前缀的容量决策。** 按真实消息身份和后端逻辑顺序选择最近最多 500 条，重复窗口/同消息详情只占一份。已核验的新 native Thinking 前缀若代表新身份，参与同一预算，淘汰最旧候选，而不是把最新前缀丢掉或永远不计它的名额。
3. **保存配对完整性。** 正文、完整详情、revision、cursor/receipt 只能在匹配的原子记录中继续作为同步缓存。淘汰不得一边删窗口行，一边继续声称旧 receipt/cursor 的完整窗口仍可复用。无法继续保持配对的同步记录应撤销该同步资格，不能篡改服务端证明；旧画面保留与可提出 delta 的资格继续分开。
4. **维护后续状态转换。** 前缀落库后同 UID 归并，不双计；超过最近 500 的当前阅读页可留页面内存，不因持久淘汰突然消失；无完整原生身份/切点的半截仍不持久化。旧未展开详情仍懒取，视觉折叠规则不变。

建议主责文件：`src/core/history-coverage.ts`、`history-sync.ts`、`display-cache.ts`，必要的 `history-details.ts`、`history-thinking-prefix.ts`。主缺陷定位：`history-coverage.ts:28–71`、`display-cache.ts:297–303, 371–386`。对 Controller/PageRecovery 的接线改动交 A-FE/主会话集中处理，不另起平行修改。

### 2.4 修改包 C：Idle Noting 的真实父 owner 全生命周期

**目标：保护仍承担有效后台维护责任的那个真实父对象，并在责任结束后正常释放；不是把所有 Agent 永久留在内存。**

输入：原报告 §5.7、§5.10，07 §8.1；原有 timer/completion/epoch/period 语义。F07 是确认缺陷；E02 先补完整序列证据，不预设一定需要改代码。

实施内容：

1. **覆盖 Gateway 的全部普通回收路径。** LRU、TTL、内存压力候选和实际 soft release 都要识别已有精确维护依赖，不能只修一个入口。复用实际 DB、Conversation、父对象、epoch、period/completion 的一致性判定，不能仅判断 timer 存在或 Main 是否 running。
2. **贯通四个阶段。** 等待 Idle 到期、Noting 已运行、正常提交后的父压缩、Framework 发布完成前；整个联合流程不能因普通回收清空 `_session_messages`、释放必要客户端或破坏 child 运行。强引用存在不能替代内容和资源仍有效的证明。
3. **解决判定与释放之间的竞态。** 维护保护检查通过/失效与实际回收要有一致的原子交接，避免“检查时无维护，释放前恰好已准入”。沿既有锁序和 owner epoch 实现；短锁不跨模型/网络等待；不复制一套维护账本。
4. **区分普通回收与显式退休。** close、替换、删除/归档等真正退休仍按原边界失效；旧回调不能消费 period、发起 admission 或清退新 owner。正常完成、取消、错误和预算结束后保护应解除，不能制造永久泄漏。
5. **把 E02 随同一次做完。** 经真实开关入口关闭 → 父对象被普通回收/timer取消 → 跨过原 due → 再开/合法 attach；证明按原语义终结旧周期、不补跑，关闭期间不 freeze/起 child。另做“只是 owner 暂不可用，应保未消费 due”的对照。**不能把这个补证需求擅自改写为‘到期前短暂关闭也必须立即删除所有未来 period’。**

主要写入归属：`gateway/run_agent_cache.py`；确需时修改现有 `secretary/noting_timers.py`、`noting_hosts.py`、`noting_scope.py`、`noting_runtime.py`、`noting_child.py`、`noting_compact.py` 与 `run_agent.py` 原 close 接缝。`gateway/run_turn_runner.py` 对 C 默认只读，避免与 D 冲突；必要窄接线由主会话协调给唯一写入者。

| 编号 | 场景族 | 结果要求 |
|---|---|---|
| C01 | 等待期、Noting运行、父压缩、Framework完成前 × TTL/LRU/pressure 三种普通回收；可参数化共用夹具 | 正式 Gateway cache 中同一真实 parent/prefix/必要资源均保持；不是另造一个“能运行”的父对象。 |

### 2.5 修改包 D：微信最终完整消息及时投递

**目标：每条完整 Assistant Message 都以自身完成时点进入发送，包括最后一条；不能把整轮结束当作消息完成时点。**

这里的“普通 stop”是模型正常结束的 final 分支，不是把用户点击 Stop 后的残片一概当成完整回复发送。原报告只确认当前最终完整消息的发送时点缺口，不把网络送达延迟或所有渠道都列为新缺陷。

输入：原报告 §5.8；用户 U11 逐完整消息及时发送原文；现有 output transform、持久化 UID、callback/FIFO、失败回执及 Turn 尾兜底。

实施内容：

1. **在内容及原生 UID 稳定的完成接缝接线。** 经既有输出变换、形成真实 Assistant 消息并达到原完整消息要求后，进入同一 callback/FIFO 通道；不能提前发送未变换文本或依赖后续 micro-compaction/cleanup/hook 完成。
2. **沿消息身份处理去重和顺序。** 普通 final 走即时通道后，Turn 尾不能再发同一 UID；不同 UID 即使正文相同也不能被误删；不按文本相等去重，不另起竞争的发送队列。
3. **保留失败与兼容语义。** 已排队/已尝试不等于发送成功，失败继续按原生机制可见；不得用尾部去重吞失败或把失败标成功。原有非微信路径、输出变换和会话内 Slash 能力保持，不借机扩大重构。

主要写入归属：`agent/turn_final_response.py`（原定位344–376）、必要 `agent/turn_finalizer.py`（618–654）、`gateway/run_turn_runner.py`（1243–1257、1921–1937）及投递测试。`agent/micro_compaction.py` 默认作为时序观察/受控等待点，不通过禁用或跳过微压缩来修发送。

| 编号 | 场景族 | 结果要求 |
|---|---|---|
| D01 | 无工具和有工具两条正式 Loop；final 已完成/持久化后阻塞 finalizer 或微压缩 | 收尾屏障未释放、Turn仍未完成时，最终完整消息已到 adapter 入口；释放后不重复。 |
| D02 | 同 UID 从即时和 Turn 尾重复到达；两条不同 UID 但正文相同；前序工具前消息 | 同一消息不重复，不同消息不漏发，既有 FIFO 顺序保持。 |
| D03 | 输出 transform、单条发送失败及既有微信 Slash 路径 | 只发送实际最终内容；真实失败不被去重吞掉/误报成功；会话管理禁用和会话内交互保留。 |

外部微信发送可以用 adapter 边界受控替身；不得 mock 掉待验证的 Loop、完整消息 callback、consumer 或 finalizer 再声称正式接线通过。证据只证明及时交给发送，不冒充真实微信网络送达测试。
